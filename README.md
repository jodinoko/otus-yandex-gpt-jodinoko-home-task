# Извлечение сущностей из юридических документов

## Запуск

Установите зависимости:

```bash
uv sync
```

Создайте файл `.env` на основе `.env.example` и укажите данные Yandex Cloud:

```env
YC_API_KEY=ваш_api_ключ
YC_FOLDER_ID=идентификатор_каталога
```

Загрузите тестовый датасет и подготовьте фрагменты документов:

```bash
uv run prepare-legal-data
```

Запустите проверку на семи документах:

```bash
uv run evaluate-legal-ner
```

Подготовленные фрагменты и итоговый отчёт сохраняются в каталоге `results`.

## Отчёт

### Датасет и подготовка текстов

В работе использован test split датасета [`TryDotAtwo/russian-legal-ner`](https://huggingface.co/datasets/TryDotAtwo/russian-legal-ner): 10 000 русскоязычных судебных документов. В датасете есть поле `text` с текстом и поле `spans` с эталонной NER-разметкой.

Длины документов:

| Показатель | Значение |
|---|---:|
| Минимальная длина | 893 символа |
| Средняя длина | 5 972,1 символа |
| Медиана | 4 772,5 символа |
| Максимальная длина | 71 254 символа |
| Длиннее 12 000 | 736 документов (7,36 %) |

Документы длиннее 12 000 символов разбиваются по границам абзацев, предложений или слов. Соседние фрагменты перекрываются на 500 символов, чтобы не потерять сущность или контекст на границе. После chunking получено 10 836 фрагментов.

### Настройка запроса к YandexGPT

В запросе использованы:

- `temperature = 0.2`, чтобы снизить случайность ответа;
- `maxTokens = 2000`;
- `jsonObject = true` для ответа в виде JSON-объекта;
- few-shot пример: после system prompt модели показаны пример документа и ожидаемый assistant-ответ, затем передаётся целевой документ.

#### System prompt

```text
Ты — строгий и точный AI-помощник юриста.
Твоя задача — извлекать факты из текста без искажений.
Используй только явно указанные данные и ничего не выдумывай.
Верни только корректный JSON без пояснений и Markdown.
```

#### User prompt

```text
Извлеки из юридического документа:

1. Участников и их роли: судья, истец, ответчик, представитель, должник и другие.
2. Организации: ООО, АО, банки, прокуратуры, налоговые и другие государственные органы.
   Для каждой организации также извлеки ИНН и КПП, если они явно указаны.
3. Финансовые сущности: задолженность, штраф, пошлина, пени, расходы и связанные с ними суммы.
4. Юридические процедуры: судебное заседание, рассмотрение, экспертиза, арест и другие.
5. Правонарушения: неуплата, вред, хищение, нарушение прав и другие.
6. Сроки обязательств: длительность в днях/месяцах или конкретная дата окончания.

Формат ответа:
{
  "participants": [{"text": "...", "role": "..."}],
  "organizations": [{"name": "...", "type": "...", "inn": "...", "kpp": "..."}],
  "financial_entities": [{"text": "...", "value": "...", "currency": "..."}],
  "legal_procedures": [{"text": "..."}],
  "offenses": [{"text": "...", "description": "..."}],
  "obligation_terms": [{"text": "...", "duration": "...", "end_date": "..."}]
}

Сохраняй значения в том виде, в котором они написаны в документе.
В поле text копируй точный фрагмент из документа.
Если данных какого-либо типа нет, верни для него пустой список [].
Если объект найден, но отдельное поле в тексте не указано, запиши в это поле null.
```

К этому тексту в конце добавляется `Юридический документ:` и сам фрагмент. Полная few-shot конфигурация находится в [`prompts.py`](src/otus_yandex_gpt/prompts.py).

### Результаты пробных запросов

Проверка выполнена на семи примерах: пять фрагментов из test split, один документ без сумм и сроков и один текст с искусственными OCR-ошибками.
Все 7 запросов завершились без HTTP-ошибок, и все 7 ответов были валидными JSON-объектами.

#### Пример успешного извлечения

Фрагмент исходного текста:

```text
ДОВЕРЕННОСТЬ

ООО «Ромашка» уполномочивает Иванова Ивана Ивановича представлять
интересы организации и подписывать заявления от её имени.
```

Полученный JSON:

```json
{
  "participants": [
    {"text": "Иванов Иван Иванович", "role": "представитель"},
    {"text": "ООО «Ромашка»", "role": "организация"}
  ],
  "organizations": [
    {"name": "ООО «Ромашка»", "type": "ООО", "inn": null, "kpp": null}
  ],
  "financial_entities": [],
  "legal_procedures": [],
  "offenses": [],
  "obligation_terms": []
}
```

Модель нашла организацию и представителя, не выдумала ИНН/КПП и вернула пустые списки для отсутствующих категорий.

#### Примеры ошибок LLM

**1. Нормализация вместо точного копирования.**

В OCR-тексте было:

```text
000 «Бета» ... Цена раб0т — 125 000 рублeй. Ср0к вып0лнения — 30 днeй.
```

Модель вернула:

```json
{
  "organizations": [
    {"name": "ООО «Бета»", "type": "ООО", "inn": "7812345678", "kpp": "781201001"}
  ],
  "financial_entities": [
    {"text": "Цена работ", "value": "125 000", "currency": "рублей"}
  ],
  "obligation_terms": [
    {"text": "Срок выполнения", "duration": "30 дней", "end_date": null}
  ]
}
```

Модель верно поняла смысл, но исправила `000` на `ООО`, `раб0т` на `работ`, `рублeй` на `рублей` и `днeй` на `дней`. Это нарушает требование копировать точный span.

**2. Поля JSON заполнены семантически неверно.**

В одном судебном документе было указано `ГРКЦ ГУ Банка России ...`, ИНН и КПП.
Модель вернула:

```json
{
  "name": null,
  "type": "ГРКЦ ГУ Банка России по <АДРЕС> области в г. <АДРЕС>",
  "inn": "<.....>",
  "kpp": "<.....>"
}
```

Структура JSON валидна, но название организации ошибочно помещено в `type`, а `name` осталось пустым.

Также встречалась нормализация окончаний и форм слов, например `Иванова Ивана Ивановича` превращалось в `Иванов Иван Иванович`.

#### Как улучшить решение

1. Поставить `temperature = 0`, чтобы ответы модели были менее случайными.
2. После ответа модели добавить простую проверку в Python:

   - все ли нужные разделы есть в JSON;
   - состоят ли ИНН и КПП из цифр нужной длины;
   - есть ли извлечённый `text` в исходном документе.

   Если проверка не прошла, такой ответ нельзя сразу использовать: нужно повторить запрос или проверить его вручную.
3. После обработки всех фрагментов удалить повторяющиеся сущности. Они могут появиться из-за перекрытия соседних фрагментов.

Для юридически важных данных в любом случае нужна дополнительная проверка человеком.

### Вывод: YandexGPT или классическая NER-модель

В проведённых экспериментах YandexGPT в целом нормально извлекал нужные сущности. Такой подход можно использовать для первичного анализа большого количества документов.
Плюс LLM в том, что список нужных данных легко изменить в промпте без обучения новой модели.

При этом модель иногда изменяла исходный текст, путала поля и могла ошибаться на тексте
с опечатками. Поэтому результаты нельзя использовать для принятия важных юридических решений без проверки человеком.

[`Natasha`](https://natasha.github.io/ner/) и [`spaCy`](https://spacy.io/usage/linguistic-features#named-entities) — могут работать локально и быстро обрабатывать много документов, но для поиска специальных юридических сущностей может потребоваться дополнительное обучение.
Также подойдут при работе с реальными юридическими документами, где необходимо соблюдать конфиденциальность. Если передавать документы во внешний сервис нельзя, лучше использовать локальную модель.

Мой вывод: YandexGPT подходит для базового анализа документов, но найденные важные данные должен дополнительно проверять человек.
